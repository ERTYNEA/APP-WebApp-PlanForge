# Architecture

The current release implements the architecture below across the existing SQL, Functions and App Service resources.

One .NET 10 solution separates Domain rules, Application use cases, Contracts DTOs, Infrastructure EF Core SQL, Azure Functions isolated HTTP and Blazor Interactive Server. The Web is a server-side BFF and never receives SQL credentials or references Infrastructure.

## Identity and session decision

The API issues cryptographically random opaque human sessions and distinct agent tokens. Only SHA-256 token hashes are stored in the existing SQL database. Human sessions survive restarts and are revocable; agent tokens expire after 30 days. The Web BFF protects the opaque session inside an HttpOnly/Secure/SameSite=Lax authentication cookie, validates it through the API on HTTP requests, and validates antiforgery before normal browser form commands. Interactive commands travel through the authenticated Blazor circuit and remain API-authorized. The key ring is persisted under the existing App Service HOME/ASP.NET/DataProtection-Keys directory, or ignored local .secrets/web-keys, so a process restart does not generate incompatible ephemeral keys. Existing SQL remains the authority for session expiry/revocation/security version. No new shared cloud secrets or Entra identities are required. Existing health/readiness responses include a non-secret actual OS process-start timestamp, allowing publication-triggered process replacement and continued session validity to be checked without a new admin restart endpoint.

API ownership authorization is mandatory for every entity and relationship. The authenticated owner is never a DTO-provided UserId. Human-only workflow approval cannot be asserted by agents.

## Notifications decision

SQL project revisions and lightweight persisted actor/action events bridge Functions changes to active Blazor views. Cancellable low-frequency API polling refreshes current views and displays actor-correct notifications. There is no claimed direct push channel from Functions to Blazor. In v0.6.0 a circuit-scoped `NotificationState` outlives page navigation without sharing notifications between sessions. Explicit `Success`, `Neutral` and `Danger` kinds determine presentation, never message substring matching. One active layout/modal host displays the deduplicated stack and a single status announcer; host handoff does not replay announcements. Notifications last six seconds, with at most four displayed. Confirmed writes retain their truthful result if a subsequent refresh fails; contextual errors do not also produce a background toast.

## Persistence

One existing Azure SQL Basic database, additive EF migrations through GitHub Actions only. Resource binaries live in SQL; independent direct Project/Phase/Subphase/Step links do not cascade-delete resources. Effective availability is the deduplicated union of a node's direct links and all structural ancestors, calculated from metadata without copying binaries or descendant links. Avatars are separate. Quotas protect the 2 GB database budget. Relational SQLite tests cover portable behavior, never substitute for SQL Server compatibility/integration evidence.

## Work-plan persistence

Projects use immutable GUIDs, owner-scoped queries and integer revision compare-and-swap inside an explicit SQL transaction. The new additive schema represents Phase, Subphase, Step and Decision as typed WorkItems with a composite project/parent foreign key. This is a normalized hierarchy, not a flat task list. Application validation requires Phase → Subphase → Step, at least one real Subphase per Phase, correct decision parents, stable record types and unique sibling order. DTOs are separate from EF entities.

A full snapshot save increments revision exactly once and retains stable IDs. Omitted records require explicit replacement. Invalid hierarchy and unauthorized ownership are rejected before writes; database collisions roll back metadata, records and events together. Short serializable read transactions keep revisions and trees consistent. Aggregate completion cannot bypass child completion or unresolved decisions; Step closure validates the project's workflow and human-only approval and stamps the authenticated actor/time. Only completed-step closure evidence is authoritative.

ProjectChanges retain the latest 100 events per project. The event and new revision are committed atomically. These events drive the observing Web view. Business HTTP adapters, agent lifecycle, CSV exchange and the Library/ZIP tranche consume this model. Library associations are independent and restrictive, orphan cleanup rechecks under the attachment row-lock protocol, and project archives verify the revision after gathering their authorized union. Bounded owner-filtered summary/change endpoints now expose actual progress and the latest 100 actor events without plan-tree/binary polling. User/agent avatars use separate raster byte storage, excluded from Library quotas/cleanup. Password changes use a concurrency-protected hash update, increment a persisted account security version and atomically revoke only the owner’s human/agent credentials. Every authentication compares the credential’s captured security version with the account, so a login or token issuance already in flight cannot escape password-change invalidation; transport/database failures are not mislabeled as stale account conflicts. The observing Web now polls bounded revision/event pages every 10 seconds while active, reloads changed snapshots and detects export events even when revision is unchanged. Polling pauses during open editors/confirmations to preserve their base revision and cancels on navigation. Exact actor messages feed deduplicated, six-second accessible toasts; no Functions-to-Blazor push channel is claimed. Blazor and streaming file BFF routes use Contracts/API only, never DbContext. The Web is cloud-published and exercised with controlled real browser accounts, not only static rendering fixtures.

## v0.2.0 lifecycle and localization

`Users.Language` is required, bounded to 16 characters and defaults to `en` for existing accounts. Only English is currently accepted. A supported-language allowlist and account-preference culture provider prepare later locale expansion without email infrastructure, Spanish resources or rewriting user-authored text. Web `Resources/UiText.resx` remains the existing UI catalog; Application `Resources/ErrorMessages.resx` separately owns safe backend-visible errors, and `Resources/ArchiveText.resx` owns the generated archive README scaffold and workflow labels without translating inserted user content. Shared modal titles, formatted confirmations, toasts and workflow labels use these resources. Native browser validation remains native.

`Agents.CredentialVersion` is an optimistic concurrency token. A credential captures that generation in `AccessCredentials.AgentCredentialVersion`; authentication compares both current account security version and, for linked credentials, the active agent’s current generation. Token persistence checks the current account generation and locks its linked-agent generation through commit; stale issuance fails409 without storing an invalid-but-apparently-valid credential. Deactivation’s final linked-token revocation runs after acquiring that same agent gate; account password changes similarly recheck revocation under the user-generation gate. This closes the gap between a prior credential scan and a concurrent insert. Reactivation cannot revive old or racing credentials. Personal unlinked tokens retain their original semantics.

Accepted linked-agent authentication captures the real minimal display name and carries it to snapshot, export and resource-change event inserts, including accepted in-flight work finishing after deletion. Physical agent deletion now acquires the shared avatar queue gate before its owner-local row, invalidates any current avatar job (retaining active-reader bytes only until safe release), backfills missing names only into real retained `ProjectChanges.ActorNameSnapshot` rows, advances each affected project once, detaches the deleted agent’s overrides to inheritance, deletes every linked credential and finally removes the agent/avatar in one transaction. Explicit unassigned and unrelated parent assignments survive. Restrictive FKs and optimistic revisions remain in force; no cascade removes business work and no operational tombstone is kept. Manual revoked/expired-token cleanup executes an owner/kind/eligibility-qualified database DELETE under Serializable without buffering all credential metadata or affecting human sessions.

Web API-origin policy admits only explicit production HTTPS and documented Development loopback scheme/host/port combinations, then guards the resolved API-prefix URI before transport. Redirects and handler cookie pooling are disabled, and headers are redacted in client logging. Antiforgery remains enabled, with Secure forced outside Development. None of this changes DNS, Entra identities, hosting architecture or external Safe Browsing classification.

## v0.4.0 effective state and immutable creation order

Only Steps have manually editable Pending/InProgress/Completed work state. In v0.4.0, one Application calculation derives effective Blocked exclusively from Pending Decisions attached to the real Project root, Phase, Subphase or Step and propagates it upward, never to unrelated siblings or innocent descendants. A blocked Step retains its base work state and valid closure evidence. Parents otherwise become Completed for a nonempty all-Completed structural child set, InProgress for partial work, or Pending (including empty parents). Resolving/deleting the last cause recalculates the graph. Legacy parent-status inputs remain enum-validated but ignored; manual Step Blocked is rejected before writes in REST, snapshots and schema1 CSV.

Effective parent states are materialized through the existing revision transaction, not independently recomputed by Home. WorkItems.CreationOrder is a server-owned immutable bigint, separate from SortOrder and last modification. The additive migration reconstructs negative historical ranks from project creation/GUID and known structural order; these are not certified original timestamps. New items receive the identity of their transaction's real ProjectChanges event. Items created together share that order. v0.4.0 breaks equal-age ties by actual Phase/Subphase/Step SortOrder hierarchy before a stable identifier, not by GUID first. Retained IDs keep stored age through moves, reorder, snapshot/CSV replacement and event pruning; incoming age is not trusted. Public CSV columns do not change.

The eighth migration introduced shadow Projects.WriteRevision with a trusted equality CHECK. The ninth v0.4.0 migration adds nullable WorkItems.ManualStatus, normalizes disposable legacy manual Blocked to Pending, reconciles effective states, increments existing project revisions once and changes the trusted fence to WriteRevision=Revision+1. Every current revision/event writer updates the offset atomically. DDL, reconciliation and fence commit together; v0.3 revision writers fail closed during SQL-to-API cutover. A failed API publication requires reviewed forward recovery, not restoration of a fenced-out writer. Existing accounts, agents and credentials are outside this migration.

## Current explorer, dashboard and form boundaries

The compact nested-list explorer uses real buttons, native keyboard navigation, expanded/current semantics and existing status badges; it does not claim the ARIA tree keyboard pattern. A contextual inspector retains CRUD, moves/order, assignments, decisions, evidence and resources at every structural level. A circuit-scoped selection store preserves manual choice and expansion. Expand all/Collapse all operate on actual structural branches without changing selection or scrolling, and deliberate choices survive passive refresh. Passive deletion selects the nearest surviving ancestor. Project-root Decisions use the actual ProjectId as ParentId, stored as a root Decision WorkItem with a null structural parent, not a fictitious Phase. PlanItem.status is base work state for Steps; effectiveStatus is the server-calculated projection used by badges, eligibility and metrics. SQL WorkItems.Status materializes effective state and nullable ManualStatus retains Step base state. Authorized Step deep links win; otherwise initial selection restores valid state, then chooses oldest InProgress, oldest Pending, or the project. Successful CSV import explicitly resets that policy. Completing the selected Step advances it; ordinary polling/edits do not jump. The page has one natural scroll; JavaScript enables inspector sticky positioning only when its actual height fits a wide viewport.

Home and Projects use distinct authorized route components with a shared view template. Reusing one parameterless component for both routes previously delayed the destination render until polling; explicit route lifetimes fix that anomaly without a loading animation or extra delay. Home reads a bounded owner-filtered SQL dashboard (three queries, no loaded plan graphs or per-project tree requests), plus a 25-project summary page. Counts now include Projects, Phases, Subphases and Steps, each with a fixed Pending/InProgress/Blocked/Completed breakdown of persisted effective states. Decisions are excluded from structural totals. Legacy literal Pending-Step and weighted Completed/Total-Step fields remain compatible; this is not an average of project percentages. All three dashboard queries share one short Serializable read transaction. At most three Pending/InProgress Steps are mixed strictly by immutable age. Recently updated covers all projects through pagination. Projects retains its searchable/filterable/sortable catalog. Active polling requests bounded change pages only for visible summaries whose event cursor advances.

Register confirms the password in the browser and authoritative antiforgery-protected BFF before forwarding the original public API request. No second password is persisted or sent to the API. Resource-backed FormError and operation-specific feedback prevent modal/background duplication; failed dialogs remain open. Conditional dialog removal restores an extant opener, current row or focusable main fallback. Shared normal/hover/focus/disabled/danger styles preserve the approved identity.

## v0.5.0 effective-state entry dates

Project and structural WorkItem rows have nullable `EffectiveStatusChangedAt` (`datetimeoffset`). A newly created entity receives the server clock instant of its initial final effective state. The common snapshot-write path recalculates the full graph, compares each retained ID's persisted effective state, and preserves the exact stored date unless that state actually changes. One injected `TimeProvider` instant supplies every transition in that operation. Revision compare-and-swap, root metadata, nodes and the actor event commit together; a relational failure rolls them all back.

A Step's hidden base-state edit while effectively Blocked does not restart its effective-state clock. Resolving the last cause establishes a new entry date even when returning to an earlier state. Unrelated edits, resources, unchanged snapshots and retained-ID CSV roundtrips preserve dates. Incoming REST dates are ignored; the schema1 CSV has no new date column. `CompletedAt`, `UpdatedAt` and immutable `CreationOrder` retain their separate meanings. Decisions themselves receive no structural state-entry date.

Migration `20261114045328_EffectiveStatusDates` adds only the two nullable columns, without defaults, data backfill, revision invalidation or a writer-fence change. Legacy dates remain unknown rather than inferred from modification/completion/age. The inspector renders `Status date unavailable` until a real transition is observed. A small interactive component formats known UTC instants through browser `Intl.DateTimeFormat`, not the Blazor server timezone; the accessible `time` element retains the full ISO UTC instant. SSR/hydration does not invent a server-local date. Browser timezone formatting handles DST and reloads; selection changes invalidate the component's formatted-value cache.

## v0.6.0 durable avatar lifecycle

Human and agent avatars remain separate from Library binaries, links and cleanup. Input is a fully decoded, MIME-matching PNG, JPEG or WebP of at most 4 MiB inclusive; animations, corrupt containers, axes above 8192 pixels and images above 16 million pixels are rejected before admission. The 40 MiB temporary-original budget belongs to the human owner and combines the personal avatar, every owned agent and old originals retained for active-reader cancellation. Final WebP bytes do not count. A singleton queue-state write gate inside Serializable transactions serializes quota reads, current-photo changes, FIFO sequence allocation and publication across API instances. Pending replacement uses net bytes; active-reader bytes remain charged until released. Library's 8 MiB/file, 100 MiB/owner and 1 GiB global defaults are unchanged.

SQL is the authority, not Azure Queue delivery order. `AvatarAdmissions` holds short-lived preparation receipts, `AvatarOptimizationJobs` holds target/generation/sequence/attempt/reader metadata, and the seeded `AvatarQueueStates` row holds global sequence, lease and fence. Existing Users/Agents retain the sole current avatar BLOB, with `AvatarGeneration` and `AvatarTemporary`. A filtered unique index permits only one current job per owner/target/kind. Migration `20261115161339_DurableAvatars` adds these three tables and four columns without rewriting existing photos, accounts, plans or Library records; old photos remain readable. Destructive downgrade is refused.

`AvatarService` validates input, persists a 30-second preparation receipt, awaits a persistent wake in `planforge-avatar-wake`, then commits the current original, new generation and SQL job under a 20-second operation bound. The original becomes official on acceptance, not after conversion. A failed signal cannot accept a new photo. A wake that arrives before the SQL commit sees the unexpired preparation as outstanding, so it is retained for redelivery; a rollback/expired preparation is harmless. The message contains only `wake`, never image bytes, target data or credentials. This is upload-driven activation through the existing `AzureWebJobsStorage`, not a periodic `TimerTrigger` or fire-and-forget task.

The deployed `AvatarWake` and `AvatarWakePoison` QueueTriggers call `DrainQueuedAsync`. A delivered message is acknowledged only when SQL has no outstanding current job, retained original or unexpired preparation. Contention, future retries and SQL failures retain that same host-delivered input instead of creating another message per failure. The separate `DrainAsync` path, used by supplemental direct-worker harnesses, creates a durable delayed successor before SQL access; it is not the production QueueTrigger entry point. Broker redelivery and SQL FIFO are deliberately separate concerns.

The worker holds an exclusive SQL session application lock (`PlanForge.Avatar.Converter`) plus a renewable 30-second SQL lease and monotonically increasing fence. A monitored session check cancels the reader if exclusion is lost; generation, current-job and fence checks prevent obsolete publication. Native Skia conversion runs through a private bounded stdio child in the same API assembly, not a new public endpoint/service. Cancellation/deadline handling joins or terminates that owned child before releasing reader bytes. The worker drains eligible jobs in SQL sequence order in bounded invocations; broker batch size one is not treated as distributed exclusion. The SQLite QA fallback is a process-local semaphore, not proof of cross-process SQL Server locking.

Pending replacement keeps its existing FIFO turn and replaces the old original; active replacement invalidates/cancels the reader and places a new generation at the global tail. Concurrent upload/delete outcomes follow the serialized commit order. Failed conversions move behind other work with bounded backoff and at most three conversion claims per generation; infrastructure wake failures do not consume conversion attempts. Expired claims are recovered under fresh exclusion/fencing. After the third failure, only the still-current generation is cleared to initials. No earlier photo is restored.

On success, the worker validates a fresh WebP (maximum 512×512, proportional, no upscaling, EXIF orientation applied, transparency retained and source metadata omitted). One SQL transaction replaces the authoritative original BLOB with WebP, changes its public version, marks the job complete and retires retained bytes. Rollback leaves the valid original, not a publication gap. Manual removal first invalidates the generation; pending bytes are removed immediately and active-reader bytes are retired only after the reader stops. The service bounds confirmation and can return 409 while removal confirmation is still pending rather than falsely reporting physical cleanup. Application deletion/optimization does not erase Azure-managed historical backups.

Public profiles expose `hasAvatar`/`avatarVersion`, and raster GET returns the current representation with a generation ETag and no-store policy. Visible `AvatarImage` surfaces poll owning-profile metadata every two seconds while the document is visible, cancel on disposal and preload a new version before swapping the displayed URL. Transient metadata failures keep the last confirmed image. Accepted upload emits one `Avatar updated` Success toast; confirmed removal emits one `Avatar removed` Danger toast. Conversion, retry, terminal removal and metadata polling never add a late optimization toast or require F5. See [API](api.md), [UI](ui-design-system.md) and [acceptance limits](acceptance.md) for the wire, interaction and evidence boundaries.

## Delivery boundary

Exact-SHA tests must succeed before ordered SQL → Functions API → Blazor deployment. Only existing GitHub repository secrets are consumed by trusted deployment jobs. Public PR tests never receive Azure credentials. Avatar wake queues use the existing Functions storage account and its already authorized access; no new storage account, identity or administrative deployment route is introduced. Queue startup capability checks are part of API readiness, while actual trigger-driven conversion remains a separate runtime acceptance check. No direct production SQL or Azure administration is required. Local SQLite/provider checks and contained queue/Functions-host probes have explicitly narrower scope than live SQL Server or Azure-scale validation.
