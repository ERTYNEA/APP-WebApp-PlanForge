# Architecture

The initial release implements the architecture below across the existing SQL, Functions and App Service resources.

One .NET 10 solution separates Domain rules, Application use cases, Contracts DTOs, Infrastructure EF Core SQL, Azure Functions isolated HTTP and Blazor Interactive Server. The Web is a server-side BFF and never receives SQL credentials or references Infrastructure.

## Identity and session decision

The API issues cryptographically random opaque human sessions and distinct agent tokens. Only SHA-256 token hashes are stored in the existing SQL database. Human sessions survive restarts and are revocable; agent tokens expire after 30 days. The Web BFF protects the opaque session inside an HttpOnly/Secure/SameSite=Lax authentication cookie, validates it through the API on HTTP requests, and validates antiforgery before normal browser form commands. Interactive commands travel through the authenticated Blazor circuit and remain API-authorized. The key ring is persisted under the existing App Service HOME/ASP.NET/DataProtection-Keys directory, or ignored local .secrets/web-keys, so a process restart does not generate incompatible ephemeral keys. Existing SQL remains the authority for session expiry/revocation/security version. No new shared cloud secrets or Entra identities are required. Existing health/readiness responses include a non-secret actual OS process-start timestamp, allowing publication-triggered process replacement and continued session validity to be checked without a new admin restart endpoint.

API ownership authorization is mandatory for every entity and relationship. The authenticated owner is never a DTO-provided UserId. Human-only workflow approval cannot be asserted by agents.

## Notifications decision

SQL project revisions and lightweight persisted actor/action events bridge Functions changes to active Blazor views. Cancellable low-frequency API polling refreshes current views and displays actor-correct notifications. There is no claimed direct push channel from Functions to Blazor.

## Persistence

One existing Azure SQL Basic database, additive EF migrations through GitHub Actions only. Resource binaries live in SQL; independent project and phase links do not cascade-delete resources. Avatars are separate. Quotas protect the 2 GB database budget. Relational SQLite tests cover portable behavior, never substitute for SQL Server compatibility/integration evidence.

## Work-plan persistence

Projects use immutable GUIDs, owner-scoped queries and integer revision compare-and-swap inside an explicit SQL transaction. The new additive schema represents Phase, Subphase, Step and Decision as typed WorkItems with a composite project/parent foreign key. This is a normalized hierarchy, not a flat task list. Application validation requires Phase → Subphase → Step, at least one real Subphase per Phase, correct decision parents, stable record types and unique sibling order. DTOs are separate from EF entities.

A full snapshot save increments revision exactly once and retains stable IDs. Omitted records require explicit replacement. Invalid hierarchy and unauthorized ownership are rejected before writes; database collisions roll back metadata, records and events together. Short serializable read transactions keep revisions and trees consistent. Aggregate completion cannot bypass child completion or unresolved decisions; Step closure validates the project's workflow and human-only approval and stamps the authenticated actor/time. Only completed-step closure evidence is authoritative.

ProjectChanges retain the latest 100 events per project. The event and new revision are committed atomically. These events drive the observing Web view. Business HTTP adapters, agent lifecycle, CSV exchange and the Library/ZIP tranche consume this model. Library associations are independent and restrictive, orphan cleanup rechecks under the attachment row-lock protocol, and project archives verify the revision after gathering their authorized union. Bounded owner-filtered summary/change endpoints now expose actual progress and the latest 100 actor events without plan-tree/binary polling. User/agent avatars use separate raster byte storage, excluded from Library quotas/cleanup. Password changes use a concurrency-protected hash update, increment a persisted account security version and atomically revoke only the owner’s human/agent credentials. Every authentication compares the credential’s captured security version with the account, so a login or token issuance already in flight cannot escape password-change invalidation; transport/database failures are not mislabeled as stale account conflicts. The observing Web now polls bounded revision/event pages every 10 seconds while active, reloads changed snapshots and detects export events even when revision is unchanged. Polling pauses during open editors/confirmations to preserve their base revision and cancels on navigation. Exact actor messages feed deduplicated, six-second accessible toasts; no Functions-to-Blazor push channel is claimed. Blazor and streaming file BFF routes use Contracts/API only, never DbContext. The Web is cloud-published and exercised with controlled real browser accounts, not only static rendering fixtures.

## v0.2.0 lifecycle and localization

`Users.Language` is required, bounded to 16 characters and defaults to `en` for existing accounts. Only English is currently accepted. A supported-language allowlist and account-preference culture provider prepare later locale expansion without email infrastructure, Spanish resources or rewriting user-authored text. Web `Resources/UiText.resx` remains the existing UI catalog; Application `Resources/ErrorMessages.resx` separately owns safe backend-visible errors, and `Resources/ArchiveText.resx` owns the generated archive README scaffold and workflow labels without translating inserted user content. Shared modal titles, formatted confirmations, toasts and workflow labels use these resources. Native browser validation remains native.

`Agents.CredentialVersion` is an optimistic concurrency token. A credential captures that generation in `AccessCredentials.AgentCredentialVersion`; authentication compares both current account security version and, for linked credentials, the active agent’s current generation. Token persistence checks the current account generation and locks its linked-agent generation through commit; stale issuance fails409 without storing an invalid-but-apparently-valid credential. Deactivation’s final linked-token revocation runs after acquiring that same agent gate; account password changes similarly recheck revocation under the user-generation gate. This closes the gap between a prior credential scan and a concurrent insert. Reactivation cannot revive old or racing credentials. Personal unlinked tokens retain their original semantics.

Accepted linked-agent authentication captures the real minimal display name and carries it to snapshot, export and resource-change event inserts, including accepted in-flight work finishing after deletion. Physical agent deletion first locks its owner-local row, backfills missing names only into real retained `ProjectChanges.ActorNameSnapshot` rows, advances each affected project once, detaches the deleted agent’s overrides to inheritance, deletes every linked credential and finally removes the agent/avatar in one transaction. Explicit unassigned and unrelated parent assignments survive. Restrictive FKs and optimistic revisions remain in force; no cascade removes business work and no operational tombstone is kept. Manual revoked/expired-token cleanup executes an owner/kind/eligibility-qualified database DELETE under Serializable without buffering all credential metadata or affecting human sessions.

Web API-origin policy admits only explicit production HTTPS and documented Development loopback scheme/host/port combinations, then guards the resolved API-prefix URI before transport. Redirects and handler cookie pooling are disabled, and headers are redacted in client logging. Antiforgery remains enabled, with Secure forced outside Development. None of this changes DNS, Entra identities, hosting architecture or external Safe Browsing classification.

## Delivery boundary

Exact-SHA tests must succeed before ordered SQL → Functions API → Blazor deployment. Only existing GitHub repository secrets are consumed by trusted deployment jobs. Public PR tests never receive Azure credentials. No Azure CLI, new identities, storage services or local SQL Server are required.
