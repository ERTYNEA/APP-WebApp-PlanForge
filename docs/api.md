# REST API

The API and Blazor BFF/UI use the same owner-authorizing backend. The v0.2.0 expansion added account language, agent credential generations and a minimum historical actor-name snapshot. The v0.3.0 eighth additive migration adds immutable item creation order and a project revision-writer fence. The ninth v0.4.0 migration adds Step ManualStatus, decision-derived effective blocking and a version04 writer offset, with transactional reconciliation. Release verification reads actual migration history and deployed versions; source code or a generated migration alone is not proof of publication.

One .NET 10 isolated Functions app is the authorizing backend. Anonymous platform triggers still require application Bearer authorization. Clients never submit an OwnerUserId. Known IDs belonging to another owner return the same safe 404 as missing records. HTTPS is mandatory outside loopback development.

## Routes

All paths below start with `/api/v1`. Bodies are JSON except raw CSV import. Authentication, parsing and ownership checks happen server-side.

- GET `/health`, GET `/ready`: liveness/version and real SQL schema readiness. Readiness also returns processStartedAtUtc from the actual OS process for non-secret restart/continuity verification.
- POST `/auth/register`: email, password, displayName; returns 201 with a human session grant.
- POST `/auth/login`: email and password; returns a new human session grant.
- GET `/auth/session`: human session profile. POST `/auth/logout`: revoke that session, 204.
- GET `/users/me`, PUT `/users/me`: human-only profile and update with `displayName` and `language`. Only `"en"` is supported; omitted language defaults to English for existing clients. Unsupported, empty or null language returns 400 before changing the profile. The preference persists per account; identity/email stay unchanged.
- POST `/users/me/password`: currentPassword/newPassword; checks the current hash and atomically revokes every human session and agent token owned by that account. Returns 204; sign in again. Another owner remains unaffected. Account/credential security versions also invalidate sessions and agent tokens issued by an already-in-flight pre-change login/request.
- GET/PUT/DELETE `/users/me/avatar`: human-only raster avatar; PUT raw bytes with image/png, image/jpeg or image/webp, at most 256 KiB. MIME/signature validation, safe inline response, independent SQL storage outside Library cleanup.
- GET `/settings`: authenticated safe product version, limits and the four ordered workflow identifiers, never credentials/configuration secrets.
- GET `/projects`: current owner's complete snapshots, retained for API compatibility. POST `/projects`: name, optional description and workflow; returns 201.
- GET `/projects/summary?skip=0&take=50`: lightweight SQL projections, description preview up to 240 characters, actual counts/progress and last event cursor, no trees or binaries. Returns items/total/skip/take/hasMore; take 1–100, skip 0–100000.
- GET `/projects/dashboard`: authenticated owner-scoped bounded SQL projection with `projectCount`, literal `pendingSteps`, `completedSteps`, `totalSteps`, weighted integer `progress` (zero for no Steps), and at most three `nextSteps`. Each focus item contains project ID/revision/name, Step ID/name/status/creationOrder and Phase/Subphase IDs/names. Pending and InProgress effective states are mixed strictly by immutable creation order; equal ages use Phase/Subphase/Step hierarchy positions before stable identifiers. Blocked/Completed are excluded. No client owner field, full trees, resource bytes or N+1 tree loading. Unauthenticated requests return 401.
- GET `/projects/{projectId}/changes?after=0`: coherent current revision, latestChangeId, resetRequired and latest 100 retained actor/action events newer than the cursor. Actor names resolve owner-local current identities; accepted linked-agent requests capture the actual name for each real event, and deletion backfills any retained legacy event without one. This also preserves events committed by an already-accepted in-flight request after agent deletion. A removed actor displays that historical name with ` (deleted agent)`. The operational agent is not retained, and no retroactive events are invented. IDs/kinds remain authoritative. A stale/pruned cursor requires refreshing the project before advancing the baseline.
- GET `/projects/{projectId}`: complete snapshot, stable IDs and revision. PUT the same route: full edited snapshot, preserving records. DELETE: `{ "revision": 1, "confirmed": true }`, permanent project/plan deletion.
- GET/POST `/projects/{projectId}/phases`, `/subphases`, `/steps`, `/decisions`: list/create typed records.
- GET/PUT/DELETE `/projects/{projectId}/phases/{id}` and equivalent subphases/steps/decisions routes: read/edit/reorder/move/delete a record. Delete requires revision and confirmed=true; descendants are intentional, and the last Subphase of a retained Phase cannot be removed.
- POST `/projects/{projectId}/completed-phases/clean`: revision and confirmed=true; removes only fully completed Phase trees.
- GET `/agents`, POST `/agents`: owner's logical agents; creation requires a human session. The Web optionally uploads an avatar through the same existing raster endpoint after creation; a failed upload must not imply that the already-created profile was rolled back.
- GET `/agents/{id}`: inspect an owner-local logical agent. PUT: human-only name/description/`isActive` update. Setting inactive revokes linked credentials and advances the agent credential generation. Reactivation never revives a revoked or in-flight old-generation token; issue a new credential. Unlinked personal tokens are unaffected.
- DELETE `/agents/{id}`: human-only, requires JSON `{ "confirmed": true }`, returns 204. This is **physical irreversible deletion**, not deactivation. It removes the agent/avatar and every linked credential row (valid, expired or revoked), detaches only its current assignment overrides to `Inherit`/null, and preserves work, Library bytes/links and real retained actor history. Affected project revisions advance once transactionally; stale saves return 409. Unrelated assignments, explicit `Unassigned`, personal tokens and other agents survive. Missing/foreign/already-deleted agents return 404; absent/false confirmation returns 400, nonhuman management 403.
- GET/PUT/DELETE `/agents/{id}/avatar`: owner-isolated safe raster read; human-only upload/removal, same 256 KiB and MIME/signature policy as account avatars.
- GET/POST `/agent-tokens`: human-only metadata listing or issuance with name and optional agentId. DELETE `/agent-tokens/{id}`: immediate revocation, 204. POST `/agent-tokens/{id}/renew`: new value and expiry, old value revoked. Issuance/renewal holds the account and linked-agent generation gates through commit; a stale generation returns 409 without persisting or returning an unusable new credential. Deactivation and account password changes perform their final revocation scan under the same row-lock protocol, so a newly committed credential cannot escape the scan and be misleadingly listed as valid.
- POST `/agent-tokens/history/clean`: human-only manual cleanup with `{ "confirmed": true }`. Physically deletes only this account’s agent-token credentials that are revoked or expired at the operation boundary, including unlinked personal tokens when eligible. Returns `{ "deletedCount": 0 }` or the actual removed count; repeating is safe. The database DELETE rechecks owner, credential kind and eligibility inside a short serializable transaction; valid tokens, human sessions and other accounts are never selected. No automatic cleanup job.
- GET `/projects/{projectId}/work-plan/export`: UTF-8 `work-plan.csv` download.
- POST `/projects/{projectId}/work-plan/import`: raw UTF-8 CSV, at most 1 MiB. Set `X-PlanForge-Replace: true` explicitly to permit omitted-record deletion. Ownership is checked before reading/parsing content. See `work-plan-csv.md`.

A plan mutation command has revision, title, parentId, optional zero-based sortOrder, description, status, assignmentMode, assignedAgentId, resolution and evidence. New Phases receive a real editable Default subphase. Subphases belong to Phases, Steps to Subphases, Decisions to the real Project root (parentId equals ProjectId) or one of those three structural types. A record ID cannot equal ProjectId. No extra Phase represents the root. Moving/reordering preserves IDs and checks the complete resulting hierarchy. Omitted sortOrder appends a new record or preserves an edited sibling position.

## Resource library and project archives

- GET `/resources`: owner metadata only, never binary Content. Search with `search`, filter `assignment=all|assigned|orphan`, and page using `skip` and `take` (default 50, maximum 100). Returns items, total, skip, take, hasMore from the actual filtered set.
- POST `/resources`: raw bytes and an allowed Content-Type. Supply `X-File-Name` as a percent-encoded UTF-8 filename and optional percent-encoded `X-Resource-Title`. Optional `X-Project-Id` and/or one of `X-Phase-Id`, `X-Subphase-Id`, `X-Step-Id` attach atomically; a structural link does not imply a direct project link. Multiple structural target headers are rejected; supplied project and structural target must agree. Targets are authorized before body reading.
- GET/PUT/DELETE `/resources/{resourceId}`: metadata, title update with current resource revision, or permanent deletion with revision and confirmed=true. Deletion removes all links deliberately; normal project/phase deletion never deletes the binary.
- GET `/resources/{resourceId}/download`: exact bytes, safe attachment filename and nosniff.
- POST `/resources/{resourceId}/links`: resource revision, attach boolean and exactly one projectId, phaseId, subphaseId or stepId. Each typed node must exist in the authenticated owner's project with the exact expected kind. Owner membership, record type and revision are checked transactionally.
- GET `/resources/usage`: owner bytes, owner budget, maximum file bytes and near-limit warning; never another user's metadata.
- POST `/resources/orphans/clean`: `{ "confirmed": true, "resourceIds": [...] }` from the preview, at most 1000 unique IDs. Returns deletedCount/skippedCount. Only owner-local zero-link resources are physically removed after a concurrent-attachment-safe recheck; no scheduled cleanup.
- GET `/projects/{projectId}/resources`: project-wide direct-plus-all-structural association union without duplicates, with each association identified. GET `/projects/{projectId}/phases/{phaseId}/resources`, `/projects/{projectId}/subphases/{subphaseId}/resources`, `/projects/{projectId}/steps/{stepId}/resources`: deduplicated effective union of that node's direct links and all ancestors, never siblings. The root route remains a project-wide association overview/export union, not a claim that phase-only files are inherited globally.
- GET `/projects/{projectId}/export`: ZIP with work-plan.csv, README.md, manifest.json and resources/{resourceId}/{safe-filename}. Includes phase-only files, excludes unrelated Library orphans and verifies a coherent project revision. Another archive in progress can return 429; a changed revision returns 409 rather than a mixed snapshot.

Defaults: 8 MiB per file, 100 MiB per owner, 1 GiB global Library reserve and 1000 files per owner. Scoped configuration keys are `ResourceLimits__MaximumFileBytes`, `ResourceLimits__OwnerBudgetBytes`, `ResourceLimits__GlobalBudgetBytes`; the global hard ceiling is 1.5 GiB to preserve headroom in SQL Basic 2 GiB. These keys require no new identity or secret and are optional. HTML, scripts and SVG MIME types are not accepted; text/Markdown/CSV, PDF, common raster images, ZIP, JSON, Office OpenXML and generic binary attachments are supported. Upload bytes are immutable; title and independent links are editable. SHA-256 and size are checked on download. Original base filenames up to 180 characters are preserved after removing path/control components; longer names are rejected, never silently truncated.

Project/structural-node deletion removes associations only. Resource cleanup never sees avatar storage. Linked-library mutations touch affected project revisions/events without overwriting plan data. Metadata listing explicitly excludes SQL binary columns; downloads and archives fetch only authorized selected resources. ZIP manifest schemaVersion 2 retains directProjectLink/phaseIds and adds typed direct itemLinks with itemId/itemTitle/kind/projectId/projectName. Inherited links are never expanded into stored manifest associations. ResourceProfile.projects and the Phase-only legacy phases view remain compatible; additive items contains all typed direct structural origins. ZIP manifests give MIME, hash and byte size; archives do not execute or automatically import resources.

## Workflow, decisions and concurrency

Workflow values are `PlanningOnly`, `LocalChangesManualApproval`, `BranchPullRequest`, `DirectToMain`, displayed in that order. Step completion requires respectively `WorkDone`, human `OwnerApproved`, `MergeConfirmed`, `PushConfirmed` evidence. Under another mode, report WorkDone explicitly with status InProgress; requesting Completed with only WorkDone is rejected 400 without a write. Agents cannot forge human approval. Changing workflow is human-only and cannot simultaneously close pending work under a more permissive mode. This records an authenticated confirmation, not automatic GitHub verification.

Only Steps accept manual Pending/InProgress/Completed. Manual Step Blocked is rejected 400 with no write/revision increment. Returned Step status is its underlying work state; effectiveStatus is the server-calculated value (client projections are ignored). A Pending Decision at Project/Phase/Subphase/Step makes that node and ancestors effectively Blocked, not its innocent descendants/siblings. Previously completed Step base/audit/evidence remains intact and is restored when the last own blocker resolves or is deleted. Parents otherwise derive nonempty all-Completed, partial InProgress, or Pending; empty parents are Pending unless blocked by an own Decision. Legacy parent inputs remain valid-enum checked but recalculated. A Step cannot newly complete while its own Decision is Pending, but a parent/root Decision does not prohibit an unblocked descendant Step from completing. Agent assignment modes remain Inherit, Override with a valid owner-local agent, or explicit Unassigned; inactive references cannot be newly assigned.

Returned PlanItem `creationOrder` is server-owned immutable age, not a timestamp, UpdatedAt or SortOrder. Existing IDs retain stored order across edit/move/reorder/import; incoming values cannot override it. New IDs receive the real mutation event identity; simultaneous creations use actual hierarchical SortOrder ties before stable identifiers. Negative historical ranks are deterministic reconstruction, not certified creation dates. The compatible schema1 CSV does not expose this field. Completed-phase cleanup uses these calculated states and returns an empty Pending project when no phases remain.

The public registration request remains email/password/displayName. The Web `/account/register` BFF additionally requires an exact nonempty confirmPassword match before contacting the API; it never persists or forwards a second secret. Native required validation and generic login/anti-enumeration errors remain unchanged.

Every mutation supplies the current revision; one successful logical operation increments it once. Stale or concurrently superseded revisions return 409. Reload and reconcile; never automatically overwrite the winner. Snapshot and child changes/events share a transaction. Export events do not increment revision. Stored events distinguish Human and Agent and use the exact action strings documented in the specification; the bounded change endpoint exposes these events; the observing Web polls this bounded cursor while active, and human observers receive actor-correct toasts without manual reload.

## Authentication and safety

Passwords require 12–128 characters. Email is normalized uniquely, display name is 1–80 characters. Human sessions expire after seven days; tokens contain 256 random bits and only SHA-256 hashes are persisted. Agent tokens expire exactly 30 days after issuance, are shown only in issuance/renewal responses, and cannot manage credentials. A disabled linked agent is rejected even in a concurrent issuance/deactivation race. The Web uses a server-side BFF, HttpOnly/SameSite cookies and antiforgery, never browser localStorage or SQL credentials. The production antiforgery cookie is explicitly Secure; only Development permits the documented HTTP loopback flow. Web-to-API configuration and final resolved request destinations must match the exact approved scheme/host/port and `/api/v1/` prefix. Production requires the existing HTTPS API origin; Development additionally permits loopback port 7601. Automatic HTTP redirects and shared handler cookies are disabled, and request headers are redacted in client logs. A redirect is an error, not permission to forward credentials.

The Web labels unlinked credentials as Personal token and linked credentials as Agent token. Valid metadata is visible by default (25 rows/page); revoked/expired history is a collapsed native disclosure (10 rows/page) with a confirmed cleanup action. The existing metadata API remains a compatible owner-local list, not a server-paginated endpoint; UI pagination does not change its response shape. Secret values appear only in the immediate issuance/renewal dialog and are discarded on dismissal.

Application-owned UI and safe error messages use standard English `.resx` catalogs. The account language drives the supported Web culture; browser/query language does not translate user content or native browser validation. Spanish and email templates are not implemented.

JSON is bounded to 64 KiB without trusting Content-Length. CSV uses a separate 1 MiB bound and strict encoding. Responses are no-store/nosniff with correlation IDs; safe problem JSON uses 400/401/403/404/409/413/429 as applicable. Unhandled exceptions do not expose SQL details, credentials or stack traces. Login/registration/API/exchange budgets are in-process per worker, not distributed anti-DDoS protection; SQL session validity is persistent across workers and restarts.

Publishing profiles, SQL credentials and cloud control-plane secrets are never part of the HTTP contract. Tokens should be injected via secure variables, never hardcoded in examples or checked into source.
