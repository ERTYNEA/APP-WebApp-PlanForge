# Deployment

All three components are published through four workflows and controlled real HTTP/browser acceptance. The initial release has six additive migrations; v0.2.0 adds `20261107010522_AccountPreferencesAndAgentLifecycle`, v0.3.0 adds the eighth `20261108082911_AutomaticPlanStateAndCreationOrder`, and v0.4.0 adds the ninth `20261108214148_DecisionBlockingAndManualStatus`. Actual application is verified from SQL history during publication. Exact-SHA deployment success, browser functionality and session/data continuity are distinct release gates; a green pipeline alone is not product acceptance.

Only GitHub Actions applies migrations or publishes Azure apps. `tests.yml` runs hermetic Release restore/build/tests on main and external PRs without Azure secrets. Its trusted-main database job calls `deploy-database.yml` only after the same SHA passes tests, when schema/database paths change or an API deployment requires reconciliation. The pipeline serializes main runs, and the database workflow serializes migrations without cancellation. Readme-only pushes do not migrate. Manual Tests dispatch requests migration reconciliation after tests.

The database job builds a self-contained EF migration bundle in Production, reads migration history before/after, and executes only pending migrations with `AZURE_SQL_MIGRATION_CONNECTION_STRING`. Every API deployment requires successful same-SHA database reconciliation, even for an API-only push: this recovers migrations left unapplied by earlier failed pushes. An up-to-date database is a no-op, not a repeated schema migration. Documentation-only pushes still do not deploy. Database and API publication reject superseded commits by checking the live main ref immediately before their state-changing operation. To roll back code, use a reviewed forward revert commit; do not rerun an obsolete pipeline over a newer deployment.

The connection stays in the runner environment, not a repository file or artifact. API runtime uses a different least-privilege SQL identity. No Azure login/OIDC or IP firewall updater is used.

The API reusable job requires successful same-SHA tests and SQL reconciliation. The Web job needs tests, scope detection, database and API jobs for the same SHA. Its first runner step executes the tested scripts/deployment-gates.py truth table: required database/API jobs must succeed; only explicitly unrequired jobs may be skipped. Failures/cancellation/pending results are never accepted. Web-only paths do not republish SQL/API; Contracts/version/SDK changes deploy both consumers in order. The fourth reusable deploy-web.yml publishes only the existing PlanForge-Web with Azure/webapps-deploy v3.0.8 and verifies HTTPS exact-SHA health, login/CSRF form, design CSS and anonymous workspace challenge. It rejects superseded main before publication. Profile preflight runs only in the trusted runner, rejects blank/REDACTED fields, verifies matching existing HTTPS SCM/public hosts and disables authenticated redirects; no credentials/settings bodies are exported. Simultaneous push triggers are not a deployment gate. Existing secret names for publication are `AZURE_FUNCTIONAPP_PUBLISH_PROFILE` and `AZURE_WEBAPP_PUBLISH_PROFILE`. Flex publication requires `sku: flexconsumption`; never create new identities to work around authentication failure.

Retain only controlled test cookies/tokens/fixture IDs for ordered publication and verify old sessions/data afterwards. Never test destructive lifecycle actions with real owner agents or credentials.

## Data protection and recovery

Never reset or drop the shared SQL database, run local database-update against it, or use real user accounts for test fixtures. Review reader/writer compatibility explicitly: additive does not automatically mean old-writer compatibility (see the v0.3.0 fence below). Inspect migration SQL, current history/schema and usage before deployment. A failure must stop dependent deployments until actual schema/history is reconciled. Prefer a forward corrective migration; do not blindly execute a generated destructive Down method.

Azure SQL Basic has managed point-in-time backups with seven-day retention as provisioned by the owner. For an accident, the human owner uses Azure portal database Restore, chooses a point before the incident, restores into a separate target, validates data/schema and plans a controlled switch. NEA has no Azure portal/CLI credentials and cannot promise this action. Do not delete the original database. Backups do not make destructive tests or cleanup buttons reversible.

Current official sources consulted: Microsoft Learn isolated worker guide, Functions GitHub Actions guide, EF applying migrations/bundles, and Azure/functions-action authentication documentation. Recheck compatibility when changing SDK/action versions.
## Runtime continuity and bounded recovery

API `/api/v1/ready` and Web `/health` expose the exact informational version/SHA and actual `processStartedAtUtc`, not host secrets or synthetic online metrics. Before a controlled publication, retain only controlled test account cookies, a valid test agent token and known project/resource IDs privately. After ordered publication, verify actual process starts later than the retained credentials, exact versions, continued old-cookie and old-agent authentication, unchanged revisions/links and exact resource hashes. Compare actual lifecycle timestamps rather than assuming the API process starts within its package-publication job. Acceptance distinguishes an observed API worker recycle from a Web replacement during publication; it does not claim an Azure Portal resource stop/start. Never delete the persistent DataProtection key ring to deploy or test restarts. App Service HOME supplies same-slot persistent keys; they are not encrypted at rest by this filesystem provider and rely on site isolation and restrictive directory access. No new shared cloud secret is introduced.

A transient first SCM read can time out before any publication. Reconcile the exact failed step and permit a bounded failed-job retry when justified; do not assume a timeout means401 or change a working profile. Successful prerequisites carried into a retry are not newly run tests/migrations. A confirmed blank/REDACTED profile or repeated authorization denial requires the owner to verify only the existing app/profile secret, not an OIDC/new identity workaround. Never export credential or app-setting bodies.

The stable required external-contributor check is `Build and test` from GitHub Actions. Existing owner bypass and all other protections remain intact. A controlled deliberately failing test on an isolated non-main diagnostic ref was executed in Actions: tests failed and all SQL/API/Web jobs had zero executed steps. Such diagnostic refs are removed after recording evidence and never merged.

## v0.3.0 transactional cutover and publication evidence

The eighth migration adds bigint WorkItems.CreationOrder plus an index on Kind/Status/CreationOrder/Id, and shadow bigint Projects.WriteRevision plus the trusted CHECK `WriteRevision = Revision`. No business tables, IDs, content, relationships or evidence are dropped. Historical negative creation ranks reconstruct project/structural order deterministically, not certified original timestamps. New records use their transaction's existing ProjectChanges identity; stored ranks survive edits/imports and event pruning, with canonical GUID ties for simultaneous creation. Calculated parent states are reconciled from Steps/decisions, and each preexisting project revision increments once to invalidate stale snapshots.

DDL, data reconciliation, revision invalidation and fence commit in one migration transaction. Old readers remain compatible, but old writers that increment only Revision (or insert a nonzero revision without the matching fence) are rejected by SQL. This deliberately fails closed during SQL→API publication rather than accepting stale aggregates/zero ages. Every new revision writer updates both columns atomically. If API publication fails after SQL, preserve the schema and complete a reviewed forward publication; do not roll back to an incompatible legacy writer or execute the destructive Down method. The short cutover window can temporarily reject plan writes. No new identity, resource, RBAC, firewall or credential change is required.

Before publication, actual generated provider commands were tested only on connection-local SQL Server #tables, including 24 recursive decision/state cases and rejected legacy insert/update writers. The self-contained migration bundle was built locally and its help exercised without applying it locally. Only the trusted Actions migrator applied production DDL. Independently read back eight migration entries, every owner's materialized aggregate against the central calculation, nonzero reconstructed ages, trusted constraint/index and unchanged runtime privileges. Protected non-QA business/credential hashes exclude only documented usage/derived fields; those derived fields are validated separately.

Release functional source `8100469cf9b75cba12714729256ec6b5be56e2c4` was published on 2026-11-08 by Actions run 42482691068, with successful ordered tests, SQL, API and Web jobs. The existing payload-verification jobs now run `scripts/payload-fingerprint.py`: a canonical path/size/content-hash manifest identifies the actual runner payload and entry assembly, rejecting symbolic links or missing assemblies. A local candidate fingerprint is not the runner artifact. Record component versions, job IDs and payload hashes in the operation report; keep repository documentation HEAD separate from actually deployed component SHA. A later docs-only commit passes applicable CI and legitimately skips unchanged binaries.

## v0.4.0 transactional state cutover and publication

The ninth migration adds nullable WorkItems.ManualStatus only to the functional work domain. Existing Step base state is retained (legacy manually Blocked test work normalizes to Pending); SQL effective status is reconciled from pending Decisions, including real-root Decisions, and existing project revisions advance once. The trusted writer fence changes atomically from equality to `[WriteRevision] = [Revision] + 1`. All new revision/event writers use that offset; v0.3 writers are rejected during the ordered SQL-to-API window. Preserve schema and complete a reviewed forward publication on API failure, never run the destructive Down or restore a fenced-out writer. Root Decision structural ParentId is null in SQL with its required ProjectId FK; the wire ParentId is the real ProjectId. ## Permanent release-documentation convention

Root `README.md` is the product introduction and advertises only the latest stable release. Root `CHANGELOG.md` is the cumulative newest-first history. Before replacing a previous README What's New section, preserve its published information in the matching changelog version section, without inventing or deleting history. Add the new changelog entry only for implemented/tested/published changes, using its actual publication date. Preserve general README functionality, architecture and documentation links; replace only obsolete release notes with the latest What's New section and a visible relative `[Full changelog](./CHANGELOG.md)` link. Do not create another version README or accumulate historical What's New sections in the root README.

Finish technical docs and CHANGELOG first; finalize README as the last substantial documentation block after actual QA/publication. Then perform final link/content checks, commit/CI and evidence packaging. Reopen a feature only for a genuine incident with tests. Future releases follow the same move-to-history/replace-latest sequence. Delivery archives are separate operation/checkpoint and documentation/evidence bundles with reviewed source/size/SHA-256 manifests, CRC and byte-fidelity checks; credentials/private fixtures/raw logs never enter them.
