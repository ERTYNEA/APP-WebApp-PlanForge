# Acceptance and operational limits

A release is not accepted solely because it compiles. The verification layers are hermetic .NET/JavaScript/pipeline regressions, controlled Azure SQL/HTTP integration, actual Blazor browser interactions, exact-SHA publication and runtime continuity. Tests never reset shared SQL or use a real owner's projects.

## Required scenarios

1. Known-GUID ownership denial across project hierarchy, decisions, agents, CSV, ZIP, resources and independent links, including authenticated Web file proxies.
2. Every Phase has a real Subphase; deleting the last retained Subphase fails without changing data.
3. Phase agent assignment inherits through descendants; overrides and explicit Unassigned remain distinct, with safe inactive references and authenticated raster avatars.
4. Each workflow independently rejects premature closure and accepts only its required work/owner-approval/merge/push evidence. An agent cannot impersonate human approval.
5. Stable-ID UTF-8 semicolon CSV exchange preserves Unicode, quotes and newlines, increments revision once, refreshes observers and rejects stale imports without overwrite.
6. Valid owner-scoped agent credentials work, renewal/revocation invalidate old values, and fixed-clock tests cover the exact 30-day expiry boundary.
7. Phase-only resources need no direct project association; deletion preserves bytes and orphan/reassignment state reflects every surviving link.
8. Confirmed completed-phase cleanup preserves active/pending work and every Library binary; confirmed orphan cleanup rechecks zero links transactionally, including real attachment races.
9. Real observing Home/Project views update without F5 and receive all five exact human/agent messages. Active work is revealed without needless scrolling, reduced motion is respected, and unchanged manual collapse is preserved.
10. Project ZIP CRC, CSV, README, manifest, exact PNG/PDF bytes, deduplication and safe paths are checked; no unrelated or foreign resource/credential is included.
11. Actual API worker recycling and publication-triggered Web process replacement preserve preexisting protected human cookies, SQL sessions, agent credentials, project revisions and resource links/bytes. Process-start UTC later than credential issuance and exact deployed SHA distinguish actual runtime continuity from a build-only result; API process start need not coincide with its package job.
12. A deliberately failing assertion on an isolated diagnostic ref fails Actions with all three deployment jobs skipped. Path/gate truth tables, trusted-main/fork boundaries, exact-SHA ordered publication and the stable required test check are verified independently.

Actual cloud-browser checks include normal project/plan forms, decisions, moves, four workflows, irreversible confirmations, token issuance/dismissal/renewal/revocation, account/avatar management, file upload/download, filters, empty states, automatic notifications and desktop/narrow layouts. A controlled collection of twenty projects was exercised and removed after inspection. All fixtures are recorded by immutable IDs before cleanup. Generated passwords, protected cookies and temporary API tokens stay private, never in this repository.

## Deliberate limits

- This is a single-owner-per-project application for a few people, not a collaboration/tenant/role platform or an agent execution service. Workflow evidence is authenticated recorded confirmation, not an automatic GitHub/provider integration.
- Default tests use relational SQLite, direct Functions handlers, bUnit and ASP.NET TestServer; they are not a local Functions HTTP host or proof of SQL Server compatibility. Separate controlled deployed-API/real-SQL/browser checks supply that evidence. No local SQL Server, Docker, Azurite or global Functions installation is required.
- Rate limits are per worker/in-process, not a distributed anti-DDoS service. Resource budgets reserve SQL Basic headroom; limits do not create new storage or a promise of zero cloud cost.
- Expiry tests advance a controlled clock; they do not claim thirty actual elapsed days. Runtime continuity tests distinguish actual worker recycling from deployment-triggered Web replacement; neither is an unperformed Azure Portal full-resource stop/start.
- DataProtection keys persist in the existing same-slot App Service HOME key directory. This filesystem key ring is not encrypted at rest by the application; site isolation and restrictive directory access apply. Protect it and do not delete it to deploy.
- Native Azure SQL seven-day PITR is disaster recovery operated by the human Azure owner. No destructive restore rehearsal or cloud cost/Insights dashboard administration is claimed. Cleanup is intentionally irreversible from the application.
- Selected text/control/focus contrast pairs are measured and actual layouts are visually reviewed; this is not an independent comprehensive WCAG certification.

For running, deployment, recovery, errors and exact wire formats, read the linked architecture, API, CSV, design and deployment documents. Publication readiness and detailed execution evidence are kept separately from source code; never place credentials or raw sensitive logs into an acceptance report.
